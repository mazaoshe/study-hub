# ADR-001：微信身份、服务端会话和机构绑定

状态：已接受

日期：2026-09-30

## 背景

V1 使用微信原生小程序、Workers 和 D1。两种业务角色为超级管理员和机构管理员；新用户必须能先通过微信认证，再兑换邀请码。机构停用后，已登录管理员的下一次请求也必须被拒绝。

## 决定

- Worker 用微信 code2Session 获取 openid，不接受客户端提交的 openid 作为身份。
- 未绑定用户的 role 和 organization_id 为 NULL，属于已认证但没有业务权限的状态，不增加第三种业务角色。
- 超级管理员由当前 SUPER_ADMIN_OPENID 配置识别。每次请求重新计算角色，配置变更立即撤销旧账号的超级权限。用户重新登录时同步数据库中的角色。
- 使用 256 位随机会话令牌，有效期 7 天。数据库保存令牌的 HMAC-SHA256 摘要，SESSION_SECRET 至少 32 字符。支持服务端退出和到期清理。
- 每次认证请求重新查询用户及机构状态，不将机构权限固化进客户端令牌。
- 普通账号最多绑定一个机构；客户端不能指定机构管理员的操作机构。
- 邀请码为随机 20 位字符，有效期 7 天、一次性使用；数据库只存摘要。兑换条件更新与用户绑定触发器在同一 SQL 操作内完成，绑定失败时整条操作回滚。
- 登录按 Cloudflare 提供的请求 IP 限流；兑换邀请码按用户限流。仅对各自接口应用限制。
- 业务表用机构与实体组成的复合外键，防止跨机构关联；流水用触发器禁止修改和删除。

## 取舍

纯 JWT 会减少一次数据库查询，但无法独立满足机构停用立即拒绝旧会话的要求。服务端会话与实时身份查询更容易明确撤销行为。尚未绑定用户保留认证能力，才能兑换邀请码。无需引入账号密码、额外身份服务或复杂权限体系。

会话、限流表是技术辅助表；正式业务表仍沿用已确认的八张核心表。本阶段创建课时相关表，但课时业务 API 留到后续阶段实现。

## 验证

本地 Workers/D1 集成测试覆盖并发兑换、同一用户竞用两个邀请码、机构隔离、过期邀请码、机构停用、用户停用、会话到期、退出和超级管理员配置变更。微信上游用受控响应替代，真实微信登录需要另外在真机验收。
